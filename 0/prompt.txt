## 2. The GitHub App callback (it is a 404 today)

After someone installs the "Resurgo Agent" App, GitHub sends them to `/auth/github/callback?code=…&installation_id=…&setup_action=install`. Build the receiving end. Checks themselves are run by a separate worker on the host. It isn't in this repo yet and gets built next, so stick exactly to the file contract below.

- **Queue directory.** Read `QUEUE_DIR` from the environment; the container mounts it at `/queue`. The API writes requests into `$QUEUE_DIR/requests/` and only reads `$QUEUE_DIR/status/`.
- **`GET /auth/github/callback`** (FastAPI, ahead of the SPA fallback):
  - Accept only an `installation_id` of 1 to 12 digits. Ignore `code` entirely; it is never stored or logged.
  - Write `$QUEUE_DIR/requests/<installation_id>.json` containing `{"installation_id": <int>, "received": "<UTC ISO time>", "setup_action": "<install|update>"}`. Write it atomically (temp file, then rename). If the file already exists, leave it alone.
  - If `requests/` already holds 50 or more files, don't write. Redirect anyway, and let the page say the queue is full.
  - Redirect (303) to `/installed/<installation_id>`. On a bad or missing id, redirect to `/`.
- **`GET /api/installations/{installation_id}`** returns `$QUEUE_DIR/status/<id>.json` if it exists. Otherwise it returns `{"installation_id": id, "state": "received"}` when a request file exists, and 404 when neither exists. The status file, written by the worker, looks like this:
  ```json
  {"installation_id": 170024627, "account": "Timidan", "updated": "<UTC ISO>",
   "state": "received|checking|done|rejected", "reason": "<why, when rejected>",
   "repos": [{"repo": "owner/name", "sha": "<12 chars>", "path": "",
              "state": "queued|checking|done|skipped", "reason": "<why skipped>",
              "run_id": "<id or null>", "result": "<runs|runs_with_gaps|broken|unsupported|null>",
              "needs_approval": false, "pr": {"url": "...", "number": 1} }]}
  ```
- **Page `/installed/:id`** (React, in the site's style):
  - Headline: "Resurgo Agent is installed."
  - Then one plain line, true to the contract: Resurgo checks each repository you picked in a fresh container, one at a time, and opens a pull request only for a fix that passed in a clean container. Code changes wait for your approval.
  - Then the live list from `/api/installations/:id`, polled every 5 seconds until the state is `done` or `rejected`. Each repo shows its state, its result badge (reuse the gallery's status styles, including "Fix verified · awaiting approval"), a link to `/runs/<run_id>` when there is one, and the PR link when there is one.
  - "received" with no list yet reads "Waiting for the runner to pick this up." "rejected" shows the reason.
  - Any motion follows docs/ANIMATION.md.
- **Compose and Dockerfile.**
  - In `deploy/compose.yaml`, mount `${RESURGO_QUEUE_DIR}` at `/queue` read-write and set `QUEUE_DIR=/queue`.
  - Run the container as `user: "1000:1000"`, the host account that owns the queue, so the worker can read and remove what the API writes. The image must still work under that user.
- **Tests.** One small API test, using FastAPI's TestClient and a temp QUEUE_DIR, that a good callback writes the request file and redirects, and that a bad id writes nothing. Run it with `uv run --with pytest --with httpx pytest -q api`, or however the repo runs its tests.
